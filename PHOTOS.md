# Photography workflow

How photos get from the camera to the `/photography/` gallery on this site.

## Where files live

```
~/Pictures/
  Library/YYYY-MM-name/      RAWs + darktable .xmp sidecars, phone/camera originals.
                             The irreplaceable originals. FLAT: one folder = one darktable
                             film roll per trip. Locations, subjects etc. are darktable tags,
                             not sub-folders. Only exception: videos/ (darktable can't tag
                             videos, so their place goes in the file name: "洱海 - MVI_7511.MP4").
  Exports/YYYY-MM-name/      Rendered JPEGs, organized by purpose:
    web/                     ← THE SITE PUBLISHES EXACTLY THIS FOLDER
    print/                   print crops / sizes
    personal/, …             anything else
```

Two kinds of sidecar sit next to the RAWs, and both are kept:
- `IMG_1234.CR3.xmp`: darktable's (edit history, tags, rating). darktable writes these "on import" and keeps them updated, so tags survive even without darktable's database.
- `IMG_1234.xmp` (no `.CR3`): **Lightroom's develop settings** (Spain, Canada, Southwest Jan '25), from before the switch to darktable. darktable ignores them. They're the only record of those edits; darktable's Lightroom import (partial: crop, exposure, white balance, …) can read them if a photo is ever re-edited.

- **Publish a photo:** put its JPEG in `Exports/<trip>/web/`.
- **Unpublish a photo:** delete it from `web/`.
- Order, cover photo and the occasional caption live in the site repo (`photos.yaml` per album, keyed by filename). Nothing else about the site lives in `~/Pictures`.
- Web-size AVIF/JPEG versions are generated by the site script and hosted on Cloudflare R2. They never go in git.

## What goes on the site

**Rule: darktable tag `app|art` minus `pii|yes`, never rejected.** Rejection beats tags: a rejected photo is out, whatever it's tagged.

| Tag | Meaning |
|---|---|
| `app|art` | Worth showing. Candidate for the site. |
| `app|print` (+ `10:8`, `1:1`, `8:10`) | Intended for printing. **Every print photo in `Library/` is also `app|art`** (print ⊆ art). The RuneScape posters (`app|fun`) are the exception. |
| `app|memory` | Keepsake, not portfolio (China). |
| `pii|yes` | Contains people / personal info. **Never publish.** |
| `places|<Country>|<Place>` | Where the photo was taken, e.g. `places|Spain|Seville`. Exported into the JPEG; **the site builds album chapters from it.** |
| `stage|final|darktable` | The darktable edit is finished. Add it when you're done editing a photo; remove it if you start re-editing. |
| `stage|final|lightroom` | Final edit was made in Lightroom; darktable's edit is NOT the real one. **Never re-export these from darktable.** (Spain; was `stage|final-lightroom` until 2026-11-12) |
| *rejected* (darktable's reject, not a tag) | **Delete eventually.** A photo can be both rejected and tagged (e.g. `app|art`); the rejection wins, so it's never published. Clean up now and then: lighttable, rating filter *rejected only*, check, then delete (to trash). |

Color labels aren't used. If photos mysteriously go missing in lighttable, check the quick-filter bar for a color-label or rating filter.

## Publishing a new trip (darktable)

Exporting is always manual. Steps:

1. **Lighttable → collections module:**
   - folder = `Library/<trip>`
   - add rule *narrow down search* → tag → `app|art`
   - add rule *exclude images* → tag → `pii|yes`
   - add rule *narrow down search* → tag → `stage|final|darktable` (only finished edits; Lightroom finals are exported from Lightroom, never darktable)
   - Top-bar rating filter: **all except rejected**. No color-label filter.
   - Check the count.
2. **Select all** (⌘A).
3. **Export module:**
   - storage: file on disk
   - path: `$(HOME)/Pictures/Exports/<trip>/web/$(EXIF.YEAR)$(EXIF.MONTH)$(EXIF.DAY)-$(FILE.NAME)`
   - format: JPEG, quality 95
   - size: 0 × 0 (full size)
   - profile: sRGB
   - style: none
   - Metadata: keep **tags + hierarchical tags** enabled in the export module's metadata preferences, so `places|…` tags reach the JPEG (the site reads them for chapters). Everything else is fine either way: the web versions are stripped of all metadata except the color profile (no GPS, no people tags).
4. Publish on the site (next section).

## Site side

One-time setup: `npm install`.

**New album:** create `content/photography/<slug>/_index.md`:

```yaml
---
title: Spain
source: 2025-03-spain          # folder under ~/Pictures/Exports/; the album = its web/ subfolder
date: 2025-03-25               # its year is shown; also orders albums (newest first)
cover_position: 50% 30%        # optional: which part of the cover to keep when cropped
cover: img-4264                # photo id = file name minus the date prefix, lowercased
captions:                      # optional, keyed by photo id
  img-4264: Baths of Doña María de Padilla, Real Alcázar, Seville
chapters:                      # optional; rendered in this order (no list = plain grid)
  - title: Andalusia
    label: Spain               # optional small label above the title
    text: Optional sentence or two of context.
    tags: [places|Spain|Seville, places|Spain|Granada]   # photos with these tags (or tags under them)
---
Optional intro paragraph (Markdown).
```

**Build + preview:**

```sh
npm run photos   # web versions → .photos-out/ (gitignored), metadata → data/photos/<slug>.json
npm run dev      # hugo server (in memory, full rebuilds) → http://localhost:1313/photography/
```

- `npm run photos` only processes new or changed JPEGs (content hash), so re-running is cheap. Photos deleted from `web/` disappear from the album and their web versions are deleted.
- Use `npm run dev`, not plain `hugo server`: Hugo 0.152 renders to disk by default, which would copy all the images into `public/`.
- Each photo gets its own page (`/photography/<slug>/<id>/`) from `content/photography/_content.gotmpl`. The lightbox keeps the URL in sync with the open photo.
- Captions, cover and chapter notes live in `_index.md`, so editing them needs no re-run. Order is chronological (true capture time).
- **Chapters** are listed in `_index.md` (`chapters:`), rendered in that order. Each selects photos by **tags** (darktable hierarchical tags, exported into the JPEGs), so one chapter can group several places (e.g. Andalusia = Seville + Ronda + Granada + Córdoba), and any tag tree works, not just `places|…`. A tag also matches the tags under it (`places|Spain` matches `places|Spain|Seville`).
  - A photo goes in the first chapter that matches; within a chapter photos are in capture order. Photos matching no chapter go last, with a build warning; a chapter matching no photos also warns.
  - Starting point: if an album has place tags but no `chapters:`, `npm run photos` prints a suggested list (one chapter per place, in trip order) to paste and then group/rename.
  - Privacy: the album data file (`data/photos/*.json`) is committed and public, so the script only records `places|…` tags plus tags the album's chapters refer to (never e.g. `subjects|people|…`). If a chapter starts using a new tag, re-run `npm run photos`.
  - Re-run `npm run photos` after changing tags in the photos; tag-only edits don't re-encode or re-upload anything (web versions are keyed by pixel content).
  - Chapters show as headings in the grid and a sticky place sidebar on wide screens. Each photo's own place (from its `places|…` tag) shows in the lightbox and on its page.
  - No `chapters:` list: sub-folders of `web/` (if any) become chapters; otherwise a plain grid.
- No GPS on the camera? Places can be inferred by matching each photo's capture time to the nearest iPhone photo's GPS (that's how Spain's were set; then written into the JPEGs with exiftool).

**Images in production** load from `params.photos.base_url` (`config/_default/params.yaml`). Locally they're served from `.photos-out/` via `config/development/`.

**Upload to R2** (after `npm run photos`, before pushing):

```sh
npm run photos:upload   # rclone sync .photos-out/ → r2:photos (bucket served at photos.donaldpinckney.com)
```

- `sync` makes the bucket match `.photos-out/` exactly. It **deletes** anything in the bucket that isn't local, so the `photos` bucket must only be used for this.
- File names contain a content hash, so files never change in place. They're uploaded with `Cache-Control: immutable` (1 year), and `--size-only` makes re-uploads fast.
- Order matters: upload first, then push the site. Otherwise the live pages briefly link to images that don't exist yet.

## Before you edit: avoid bulk auto-styles

The `AUTO SIMPLE` style sets the exposure module to **automatic** (deflicker mode, target −2.5 EV). That's meant for time-lapses and makes dark, moody scenes look washed out. Spain's darktable history is mostly this style and was never hand-edited. Keep styles for things that are the same on every photo (lens correction, denoise, sharpening, a deliberate color grade), never for exposure or white balance. Prefer auto-apply module presets over styles for lens correction.

## Locations within a trip (China)

Places are tags, never folders: `places|China|<province>|<place>`, in Chinese, at most two levels below the country, and geographically correct (e.g. 织金 is `贵州|织金`, not under 贵阳 even though it was a day trip from there). Display names (e.g. English) belong in the album's YAML, not in the tags. Album chapters select and group these tags (e.g. a 大理 chapter listing `云南|大理`, `云南|洱海`, `云南|喜洲镇`, …).
